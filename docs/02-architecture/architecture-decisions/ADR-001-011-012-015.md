# ADR-001: Rust as Backend Language

| Field | Value |
|-------|-------|
| **ADR ID** | `ADR-001` |
| **Status** | `ACCEPTED` |
| **Date** | 2026-10-02 |
| **Related** | ADR-002, ADR-003, ADR-012 |

## Context
We need a backend language for a real-time messaging platform that handles thousands of concurrent WebSocket connections, processes messages with sub-millisecond latency, and runs 24/7 with high reliability.

## Problem
Select a backend programming language that maximizes: concurrency performance, memory safety, runtime reliability, and developer control over system resources.

## Options Considered

| Option | Pros | Cons |
|--------|------|------|
| **Rust** | Memory safety without GC, predictable latency, zero-cost abstractions, async/await with Tokio, strong type system | Steeper learning curve, slower initial development, smaller ecosystem than Go/Node |
| **Go** | Fast compilation, goroutines, simple concurrency, large ecosystem, fast development | GC pauses (unpredictable latency spikes), less expressive type system, error handling verbosity |
| **Node.js (TypeScript)** | Same language as frontend, huge ecosystem, fast development | Single-threaded event loop, GC pauses, CPU-bound work blocks event loop, weaker at sustained high-throughput |
| **Erlang/Elixir** | Built for messaging (BEAM VM), OTP supervision, hot code reloading, per-process GC | Different paradigm, smaller hiring pool, interop complexity with existing tools |
| **Java/Kotlin** | Mature ecosystem, JVM performance, Netty for async | JVM startup time, memory overhead, GC tuning complexity |

## Decision
**Rust** is the backend language.

## Reasons
1. **No garbage collector:** WebSocket-heavy workloads need predictable latency. GC pauses in Go, Java, or Node.js can cause latency spikes during sustained load. Rust's ownership model provides memory safety without runtime GC.
2. **Async concurrency via Tokio:** Tokio provides an M:N green-thread executor that efficiently handles 10K+ concurrent connections on a single instance. This matches our WebSocket workload profile.
3. **Type system:** Rust's type system (enums, pattern matching, Result/Option) makes invalid states unrepresentable, reducing runtime errors in message handling logic.
4. **Performance:** For message routing, validation, and serialization, Rust achieves performance comparable to C/C++ without sacrificing safety.
5. **Single binary deployment:** No runtime dependency (JVM, Node.js runtime). Simpler deployment, smaller container images.
6. **Portfolio value:** Demonstrates systems-level engineering capability.

## Consequences
- **Slower initial development** compared to Go or Node.js. Mitigated by strong documentation and architecture design upfront.
- **Learning curve** for contributors unfamiliar with ownership/borrowing. Mitigated by coding standards and examples.
- **Smaller crate ecosystem** for some domains (e.g., push notifications). May need to use HTTP clients to call external APIs directly.

## Alternatives Rejected
- **Go:** Would be suitable but lacks the latency predictability and type expressiveness we want. Go would be reconsidered if we needed a separate, simple background service (e.g., a metrics aggregator).
- **Erlang/Elixir:** Excellent for messaging but introduces a second language/runtime. ADR-012 explains how we achieve supervision-like patterns in Rust.
- **Node.js:** Single-threaded event loop is a bottleneck for CPU-bound message processing at scale.

## Reconsider When
- If the team grows and Rust becomes a hiring bottleneck
- If a specific service has requirements better served by another language (document in a new ADR)

# ADR-011: Modular Monolith Architecture

| Field | Value |
|-------|-------|
| **ADR ID** | `ADR-011` |
| **Status** | `ACCEPTED` |
| **Date** | 2026-10-02 |
| **Related** | ADR-001, ADR-013 |

## Context
We need to decide how to structure the backend: as a microservices architecture with independent deployable services, or as a monolith with internal module boundaries.

## Problem
Balance development speed, operational simplicity, and future scalability for a project built by a solo developer / small team.

## Options

| Option | Pros | Cons |
|--------|------|------|
| **Modular Monolith** | Single deployment, simple debugging, no network serialization overhead, shared database, fast development | Harder to scale individual components, single failure domain for compute |
| **Microservices** | Independent scaling, independent deployment, technology diversity, team independence | Network overhead, distributed transactions, service discovery, operational complexity, debugging difficulty |
| **Serverless Functions** | Auto-scaling, pay-per-use, no server management | Cold starts, state management complexity, WebSocket limitations, vendor lock-in |

## Decision
**Modular Monolith** with documented extraction criteria.

## Reasons
1. **Team size:** A solo developer or small team cannot justify the operational overhead of 5-10 microservices.
2. **Shared database:** All features (auth, messaging, groups) need the same PostgreSQL instance. Microservices would either share a database (defeating the purpose) or require distributed transactions.
3. **Development speed:** Function calls are faster than HTTP requests. Debugging a single process is simpler than tracing across services.
4. **Module boundaries provide the key benefit:** Clean interfaces between modules (auth, messaging, media, calls) provide the same logical separation as microservices without network overhead.
5. **Extraction is always possible later:** If media processing needs its own scaling profile, the media module can be extracted into a separate service because it communicates with the rest via well-defined trait interfaces.

## Module Structure

```
backend/
├── src/
│   ├── main.rs
│   ├── config/
│   ├── domain/         # Shared types (User, Message, etc.)
│   ├── auth/           # Authentication module
│   │   ├── handlers.rs
│   │   ├── service.rs
│   │   └── repository.rs
│   ├── messaging/      # Messaging module
│   ├── groups/         # Groups module
│   ├── media/          # Media module
│   ├── calls/          # Call signaling module
│   ├── presence/       # Presence module
│   ├── notifications/  # Push notifications module
│   ├── websocket/      # WebSocket connection management
│   ├── workers/        # Background workers
│   ├── middleware/      # Axum middleware
│   └── infrastructure/ # DB, Redis, R2 clients
```

## Consequences
- Single process: if the Axum process crashes, everything is unavailable (mitigated by supervisor auto-restart)
- All modules share the same resource limits (CPU, memory)
- Cannot scale messaging independently of auth (acceptable at current scale)

## Extraction Criteria
Extract a module when:
1. Its resource profile (CPU, memory) differs significantly from other modules
2. Its deployment frequency is much higher/lower than other modules
3. Its failure should not affect other modules
4. A separate team needs to own it independently

## Reconsider When
- Sustained load exceeds what a single instance (vertically scaled) can handle
- A specific module (e.g., media transcoding) needs different compute resources

# ADR-012: Erlang-Inspired Supervision in Rust

| Field | Value |
|-------|-------|
| **ADR ID** | `ADR-012` |
| **Status** | `ACCEPTED` |
| **Date** | 2026-10-02 |
| **Related** | ADR-001, ADR-002 |

## Context
Erlang/OTP provides a battle-tested supervision model where processes are organized in trees, and a supervisor automatically restarts failed children. We want similar fault tolerance in our Rust backend.

## Problem
How do we achieve automatic worker recovery, failure isolation, and structured concurrency in Rust?

## Decision
Implement Erlang-inspired supervision patterns **manually** in Rust using Tokio primitives. Do NOT introduce Erlang or the BEAM VM.

## What Rust Provides vs. What We Build Manually

| OTP Concept | Rust Equivalent | Built-in? |
|-------------|----------------|-----------|
| Process | `tokio::task` | ✅ Built-in |
| Process mailbox | `tokio::sync::mpsc` channel | ✅ Built-in |
| Supervisor | Custom `Supervisor` struct managing `JoinHandle`s | ❌ Manual |
| GenServer | Custom trait with message loop | ❌ Manual |
| Process linking | `JoinHandle::await` + error detection | ⚠️ Partial |
| Restart strategies | Custom logic (one-for-one, one-for-all) | ❌ Manual |
| Exponential backoff | Custom with jitter | ❌ Manual |
| Process isolation | Tokio tasks are isolated; panics don't propagate to other tasks | ✅ Built-in |
| Hot code reloading | NOT available in Rust | ❌ Not possible |

## Supervision Tree Design

```
RootSupervisor
├── ConnectionManager (manages WebSocket connections)
├── MessageWorker (processes message send/delivery)
├── PresenceWorker (manages online/offline presence)
├── NotificationWorker (sends push notifications)
├── CallSignalingWorker (manages call state machines)
├── MediaWorker (processes uploads, thumbnails)
└── CleanupWorker (expired tokens, old data)
```

## Supervisor Implementation Pattern

```rust
struct Supervisor {
    workers: Vec<WorkerHandle>,
    restart_counts: HashMap<String, (u32, Instant)>,
    max_restarts: u32,
    max_restart_window: Duration,
}

impl Supervisor {
    async fn run(&mut self) {
        loop {
            // Wait for any worker to finish
            let (worker_name, result) = self.wait_for_any_worker().await;
            
            match result {
                Ok(()) => {
                    // Worker finished normally
                    tracing::info!(worker = %worker_name, "Worker completed");
                }
                Err(e) => {
                    // Worker panicked or returned error
                    tracing::error!(worker = %worker_name, error = %e, "Worker failed");
                    
                    if self.should_restart(&worker_name) {
                        let delay = self.backoff_delay(&worker_name);
                        tokio::time::sleep(delay).await;
                        self.restart_worker(&worker_name).await;
                    } else {
                        tracing::error!(
                            worker = %worker_name,
                            "Max restarts exceeded, not restarting"
                        );
                    }
                }
            }
        }
    }
}
```

## Consequences
- We get ~80% of OTP supervision benefits without introducing a new runtime
- No hot code reloading (acceptable: we use rolling deployments)
- Manual implementation means we must write and test supervisor logic ourselves
- Tokio task isolation provides panic containment: a panicking worker does not crash the process

## Reconsider When
- If we need distributed supervision (multiple nodes coordinating worker placement)
- If fault tolerance requirements exceed what Tokio tasks can provide
- If the team has Erlang/Elixir expertise and the complexity is justified

# ADR-015: Message Idempotency via Client-Generated ID

| Field | Value |
|-------|-------|
| **ADR ID** | `ADR-015` |
| **Status** | `ACCEPTED` |
| **Date** | 2026-10-02 |
| **Related** | ADR-016, MSG-001 |

## Context
In a real-time messaging system, network unreliability means clients will retry sending messages. Without idempotency, retries can create duplicate messages.

## Problem
How do we prevent duplicate messages when a client retries a send operation?

## Options

| Option | Pros | Cons |
|--------|------|------|
| **Client-generated UUID** | Simple, no round-trip for ID, client can retry freely | Clients must generate valid UUIDs |
| **Server idempotency key** | Server controls ID generation | Requires round-trip or separate idempotency header |
| **Content-based dedup** | No client-side ID needed | Same user sending same content = false positive |
| **No dedup (last-write-wins)** | Simplest | Duplicates appear in conversation |

## Decision
**Client-generated UUID v7** as `client_message_id`, with a UNIQUE constraint on `(conversation_id, client_message_id)`.

## Implementation
1. Client generates UUID v7 before sending
2. Server attempts `INSERT ... ON CONFLICT DO NOTHING`
3. If conflict: server returns the existing message (same as a new send from client's perspective)
4. UNIQUE constraint enforces idempotency at the database level, which is the lowest and most reliable layer

## Consequences
- Clients MUST generate valid UUID v7 values
- The UNIQUE constraint adds a small overhead to every INSERT (index check)
- Idempotency is guaranteed even across server restarts (it's in the database)
- Works correctly across multi-device (each device generates its own UUID)
